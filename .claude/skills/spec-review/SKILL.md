# spec-review — 스펙·플랜 리뷰 루프

출처: Agentic Engineering 1주차 2교시 (1-2 14:11~15:12, 31:37~32:34)

## 입력

- `/spec-review <스펙 파일>` → **스펙 모드**: 스펙 자체의 맹점을 찾는다.
- `/spec-review <플랜 파일> <스펙 파일>` → **플랜 모드**: 플랜이 스펙을 빠짐없이·어긋남 없이 따르는지 본다.
- 파일이 없거나 경로가 틀리면 멈추고 묻는다. 내용을 짐작해서 만들지 않는다.
- `docs/adr/`가 있으면 리뷰어에게 같이 넘긴다. ADR과 어긋나는 건 P0다.

## 루프 (최대 3라운드)

1. **리뷰 맡기기** — Agent 도구로 새 서브에이전트를 띄운다. 넘기는 것은 파일 경로와 아래 "리뷰어 지시"뿐이다.
   내 의견·의도·예상 답은 넘기지 않는다 (넘기면 리뷰어가 내 결론을 확인만 해 온다).
2. **분류하기** — 받은 지적을 하나씩 아래 규칙으로 처리한다.

   | 등급 | 처리 |
   |---|---|
   | **P0** (이대로 구현하면 틀린 것을 만들거나, 깨지거나, 보안·데이터 손실) | 무조건 문서를 고친다 |
   | **P1** 중 실제로 일어날 것 + 문서 수정으로 바로 고칠 수 있는 것 | 고친다 |
   | **P1** 중 전체 설계를 바꿔야 하는 것 | 고치지 않고 `issues.md`에 적는다 (아래 형식) |
   | **P1** 중 "이럴 수도 있다" 수준 / **P2** | 건너뛴다. 보고에 개수만 적는다 |

   - 고치려면 **무엇을 할지 골라야 하는** 지적(모순된 두 요구 중 하나, 정해지지 않은 기술·제품 선택)은 내가 고르지 않는다. 문서에 `❓결정 필요: <선택지>`로 표시하고, 끝날 때 사용자에게 묻는다. 의사결정은 사람이 한다.
   - 이슈는 하나씩 따로 처리하지 않는다. **같은 영역**끼리 `issues.md`의 한 제목 아래 묶는다 (나중에 PR 하나로 처리할 단위).
   - 리뷰어 지적이 틀렸다고 판단하면 고치지 말고, 왜 틀렸는지 한 줄로 보고에 남긴다.
3. **멈출지 판단** — 이번 라운드에 고친 P0·P1이 **0개**면 멈춘다. 아니면 수정된 문서로 1로 돌아간다 (매 라운드 새 서브에이전트).
4. 3라운드를 돌고도 P0가 남으면 멈추고 사용자에게 남은 P0를 보여 준다. 혼자 더 돌지 않는다.

## 리뷰어 지시 (서브에이전트 프롬프트에 그대로 넣는다)

> 너는 이 문서를 처음 보는 리뷰어다. 칭찬은 하지 말고 결함만 찾아라.
> [스펙 모드] 이 스펙대로 구현하는 에이전트가 엉뚱한 것을 끝까지 만들게 될 맹점을 찾아라:
> 모호한 요구, 빠진 끝나는 조건, 서로 모순되는 문장, 정의되지 않은 입력·에러·경계값, 검증 방법이 없는 요구.
> [플랜 모드] 플랜이 스펙의 모든 요구를 다루는지, 스펙에 없는 것을 추가했는지, 순서·의존이 틀렸는지 찾아라.
> 각 지적은 `등급(P0/P1/P2) | 위치(문서의 절·줄) | 문제 | 실제로 일어날 상황 한 줄 | 고칠 방향` 한 줄로 써라.
> 결함이 없으면 "결함 없음"이라고만 써라. 파일은 읽기만 하고 고치지 마라.

## issues.md 형식

```markdown
## <영역 이름>
- [ ] <문제 한 줄> — <설계가 필요한 이유> (spec-review <날짜> 라운드 N)
```

## 끝날 때 보고

- 라운드 수, 멈춘 이유 (P0·P1 없음 / 3라운드 상한)
- 고친 것: 등급 · 한 줄씩
- `issues.md`로 넘긴 것: 영역별 개수
- 건너뛴 P1·P2 개수, 리뷰어가 틀렸다고 본 지적
- `❓결정 필요` 목록 — 사용자에게 하나씩 묻는다
